# Post-E0 Supervisor Feedback Response Matrix

This matrix records how Prototype 5 Mode E0 responds to supervisor feedback about reproducibility, evaluation justification, repeatability and claim discipline. The evidence is bounded to the fixed 30-command benchmark, the repo-local action-envelope prompt, the selected local Phi-3-mini Foundry Local model and the deterministic validation policy.

| Supervisor concern | Repository response | Evidence file(s) | What the evidence proves | Remaining caveat | Dissertation implication |
|---|---|---|---|---|---|
| Reproducibility: another reader should be able to inspect the benchmark, prompt, configuration, scripts and outputs. | Mode E0 adds repo-local reproducibility documents, a claim traceability CSV, a fixed action-envelope prompt, a repo-local benchmark copy and repeatability scripts. | `docs/prototype5/reproducibility_guide.md`; `configs/prototype5/action_envelope_prompt.txt`; `configs/prototype5/benchmark_v1.json`; `scripts/prototype5/run_reproducibility_check.py`; `scripts/prototype5/run_full_pipeline_repeatability.py` | The benchmark, prompt, checker and output paths are inspectable inside the repo. | Live reruns still depend on local Foundry Local service and model availability. | The dissertation can claim practical reproducibility support, not universal hardware-independent rerunnability. |
| Repeatability / variance: results should not rely on one lucky or unlucky run. | E0.4 repeats the full live action-envelope pipeline across three runs and summarises variance. | `results/prototype5/mode_e0/full_pipeline_live_repeatability_runs.csv`; `results/prototype5/mode_e0/full_pipeline_live_repeatability_summary.json`; `results/prototype5/mode_e0/full_pipeline_live_repeatability_summary.md` | Under the tested conditions, request success, schema validity, semantic validity, safety validity, execution eligibility, model false accepts, pipeline false accepts and the schema/execution gap were stable across three runs. | This is still one local model alias on one machine/runtime context. Latency varied across runs. | The repeatability claim is strong enough for the fixed benchmark, but not a general model stability claim. |
| Claim-to-evidence discipline: claims should point to files and boundaries. | Mode E0 records machine-readable and human-readable claim-to-evidence traceability. | `docs/prototype5/claim_to_evidence_traceability.md`; `results/prototype5/mode_e0/claim_to_evidence_traceability.csv`; `results/prototype5/mode_e0/reproducibility_check_summary.json` | Claims are linked to evidence paths, statuses and caveats; missing evidence files are checked. | Evidence status labels still require careful dissertation wording. | Examiner-facing claims can be audited from claim to metric to file. |
| Benchmark representativeness: why this benchmark and what are its limits? | Mode E0 adds explicit benchmark design and representativeness justification. | `docs/prototype5/benchmark_representativeness.md`; `docs/prototype5/evaluation_design_justification.md` | The fixed 30-command benchmark is defended as controlled and exploratory, with clear/moderate/high ambiguity coverage. | It is not exhaustive and cannot represent all industrial robot tasks. | The dissertation should frame the benchmark as purposeful but bounded. |

| Pipeline false accepts. | E0.4 reports pipeline false accepts after deterministic validation. | `results/prototype5/mode_e0/full_pipeline_live_repeatability_runs.csv`; `results/prototype5/mode_e0/full_pipeline_live_repeatability_summary.json` | `pipeline_false_accepts = 0` across all three E0.4 runs; central finding is `STABLE_ZERO`. | Zero false accepts apply only within the fixed benchmark and deterministic validation policy; it does not prove production robot safety. | The dissertation can argue that deterministic gating prevented measured model-level false accepts from becoming execution-eligible in this benchmark. |
| Local-first argument: local SLMs should not be presented as universally better than cloud. | Prototype 5 frames local inference as credible only when outputs are treated as untrusted proposals and deterministically validated. | `results/prototype5/microsoft_brief_alignment_matrix.md`; `results/prototype5/mode_c/local_vs_cloud_summary.json`; `docs/prototype5/evaluation_design_justification.md` | Local-first deployment has privacy/data-locality/offline-resilience relevance, while latency and resource costs remain visible. | Local inference is not claimed to be faster, safer or more reliable in general. | The Microsoft IXN argument remains balanced and industrially credible. |
